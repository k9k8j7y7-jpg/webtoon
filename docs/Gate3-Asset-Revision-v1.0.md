## 배경 및 핵심 원칙

게이트 3 테스트 결과, **"생성 전에 사용자가 방향을 정하는 단계"가 빠져 있음**을 확인했다. 현재는 대본에서 캐릭터·장소를 자동 추출해 AI가 외모·장소·스타일을 임의 확정하며, 사용자가 방향을 지정할 수 없다.

**변경 원칙:**
```
현재:  대본 → AI가 임의 생성 → 표시  (사용자 개입 0)
개선:  스타일 선택 → 조건 입력 → 생성 → 결과 확인 → 조건 바꿔 재생성
```

게이트 3 화면의 섹션 순서를 다음으로 재배치한다:
```
[1] 스타일 선택   (맨 위로 이동)
[2] 캐릭터 시트   (조건 입력 폼 추가)
[3] 장소 레퍼런스 (제안 → 편집)
[4] 자산 승인 → 다음 단계
```

## 수정 1. 캐릭터 조건 입력 폼

### 목적
캐릭터 생성 전, 인물별 조건 입력 폼을 제시한다. "중간 구조화"(선택 필드 + 자유 서술).

### 데이터 모델 변경 — `characters` 테이블
`Data-Model 4.1`의 단일 `description TEXT`를 구조화 속성으로 확장한다.

```sql
ALTER TABLE characters
  ADD COLUMN gender       VARCHAR(20)  AFTER name,   -- 성별
  ADD COLUMN age_group    VARCHAR(20)  AFTER gender, -- 나이대: teen/20s/30s/40s+
  ADD COLUMN hair_style   VARCHAR(50)  AFTER age_group,
  ADD COLUMN hair_color   VARCHAR(50)  AFTER hair_style,
  ADD COLUMN body_type    VARCHAR(30)  AFTER hair_color, -- 체형: slim/normal/sturdy
  ADD COLUMN mood         VARCHAR(50)  AFTER body_type,  -- 분위기/성격
  ADD COLUMN detail_notes TEXT         AFTER mood;       -- 자유 서술(세부 특징)
-- 기존 description 은 유지(하위호환) 또는 detail_notes 로 마이그레이션
```

### 프론트엔드
- 캐릭터 카드에 **[조건 편집]** 버튼 추가. 클릭 시 입력 폼(모달 또는 인라인):
  - 선택 필드(드롭다운/버튼): 성별, 나이대, 헤어스타일, 헤어컬러, 체형, 분위기
  - 자유 서술칸: `detail_notes` — placeholder 예시 필수 (수정 6 참조)
- 재생성 버튼은 "현재 조건으로 재생성" + "조건 수정 후 재생성" 둘 다 가능하게.

### 백엔드 — Prompt Engine
- 캐릭터 시트 생성 프롬프트를 `description` 단일 텍스트가 아니라, 위 구조화 필드 + `detail_notes`를 조합해 구성.
- 예: `"{age_group} {gender}, {hair_color} {hair_style} hair, {body_type} build, {mood} mood. {detail_notes}"`

### API — `API-Spec 5장`
- `POST /episodes/{id}/characters` 요청 바디에 인물별 조건 필드 추가.
- `PUT /characters/{id}` (조건 수정) 엔드포인트 추가 또는 기존 활용.
- `POST /characters/{id}/regenerate` 에 조건 변경 반영.

## 수정 2. 스타일 선택을 맨 위로 + 썸네일

### 목적
스타일이 화풍을 결정하므로 캐릭터·장소 생성보다 **먼저** 확정되어야 한다. 현재 맨 아래 → 맨 위로 이동.

### 프론트엔드
- 게이트 3 진입 시 **스타일 섹션을 최상단**에 배치.
- 스타일 미확정 상태에서는 캐릭터·장소 "생성" 버튼 비활성화 → 스타일 선택 후 활성화.
- 각 스타일 버튼에 **예시 썸네일 이미지** 표시. (정적 샘플 이미지, 스타일당 1장 — 별도 준비)

### 백엔드
- 스타일 확정을 캐릭터·장소 생성의 **선행 조건**으로 강제.
- `styles` 테이블은 이미 에피소드 단위(`Data-Model 5.2`)라 구조 변경 불필요. 저장 시점만 앞으로.

## 수정 3. 스타일 확장 (코어 3 + 베타 12)

### 목적
`PRD 5.1`의 2층 구조를 복원한다. 현재 코어 3개만 노출, 확장 베타 12개 누락.

### 구현
스타일 프리셋 정의(상수/설정 또는 `styles` 시드 데이터)에 다음을 추가:

**코어(3):** korean_webtoon(한국 웹툰) · romance(로맨스) · sd(SD 개그)

**확장 베타(12), `tier='beta'` + `[베타]` 뱃지:**
kakao(카카오풍) · emotional_romance(감성로맨스) · shonen(소년만화) · realistic(반실사) · anime(아니메풍) · marvel(마블풍) · watercolor(수채화) · fantasy_rpg(판타지RPG) · pixel(픽셀아트) · western_fantasy(서양판타지) · cyberpunk(네온 사이버펑크) · storybook(그림책풍)

### 프론트엔드
- 코어는 상단 "추천"으로, 베타는 카테고리 아코디언으로 그룹핑 (`PRD 5.2` UI 참조).
- 베타 스타일에 `[베타]` 뱃지 표시.

### 참고
- `styles.tier` 필드(`Data-Model 5.2`)는 이미 `ENUM('core','beta')` 존재. 활용.
- 반실사·극화 포함해 일단 전부 노출. 코어 승격/제거는 실제 생성 결과 보고 나중에 수동 판단.
- 각 스타일의 `prompt_snippet`은 실제 생성 테스트하며 튜닝.

## 수정 4. 장소 "AI 제안 → 사용자 편집"

### 목적
현재 대본에서 장소를 자동 추론·확정(대본에 명시 없어도 생성). AI 제안을 사용자가 편집 가능하게.

### 프론트엔드
- 장소 생성을 2단계로:
  1. **제안 단계:** AI가 필요 장소 목록 제안 → 사용자가 추가/삭제/이름수정
  2. **생성 단계:** 확정된 목록으로 레퍼런스 이미지 생성
- 각 장소에 간단한 분위기 서술칸 (선택) — placeholder 예시 필수 (수정 6).

### 데이터 모델 — `locations` 테이블
분위기 서술 필드 추가:
```sql
ALTER TABLE locations
  ADD COLUMN mood_notes TEXT AFTER description;  -- 분위기 서술 (예: "따뜻한 오후 햇살")
```

### API — `API-Spec 5장`
- 장소 제안/생성을 분리:
  - `POST /episodes/{id}/locations/suggest` — AI 제안 목록 반환 (텍스트, 무료)
  - `POST /episodes/{id}/locations` — 확정 목록으로 이미지 생성 (기존, 비동기)
- `PUT /locations/{id}` — 이름·분위기 수정.

### 백엔드 — Prompt Engine
- 장소 생성 프롬프트에 `mood_notes` 반영.

## 수정 5. 스타일을 캐릭터·장소·컷 전부에 적용

### 목적
스타일(글로벌 락)이 캐릭터·장소 생성 프롬프트 양쪽에 실제 주입되도록 한다. 현재 순서 문제로 주입이 불명확.

### 백엔드
- 캐릭터 생성·장소 생성 시, 해당 에피소드의 `styles.prompt_snippet`을 프롬프트 앞에 **동일하게 주입**.
- 한 에피소드 = 하나의 화풍. 캐릭터·장소·컷 전부 동일 스타일.
- `used_references`에 `style:{preset_key}` 포함 (이미 `Cut-Spec 2.10` 설계됨 — 캐릭터·장소 생성 로그에도 반영).

### 참고
- 구조(에피소드 단위 styles)는 이미 맞음. 수정 2(순서 앞으로)와 함께 처리하면 자연 해결.

## 수정 6. 입력칸 예시 placeholder

### 목적
"그림 못 그려도 웹툰" 철학. 초보가 무엇을 입력할지 알 수 있게 흐린 예시 텍스트 제공.

### 프론트엔드
- 캐릭터 자유 서술(`detail_notes`): `placeholder="예: 은테 안경, 왼쪽 눈 밑 점, 항상 후드티"`
- 장소 분위기 서술(`mood_notes`): `placeholder="예: 따뜻한 오후 햇살이 드는, 아늑한 분위기"`
- 그 외 자유 입력칸 전반에 예시 placeholder 적용.

## 수정 7. 장소 정체성 교체 처리 (MVP 범위 한정)

### 목적
장소 수정을 두 종류로 구분하고, MVP 범위를 명확히 한다.

### 구현
- **분위기 조정** (같은 장소, `mood_notes` 변경): 대본 영향 없음 → 자유 수정 허용. **MVP 포함.**
- **정체성 교체** (장소 이름 변경, 예: 욕실→공원): 대본과 모순 → MVP에서는 **막고 안내**.
  - 장소 이름(정체성) 변경 시도 시: `"장소를 다른 곳으로 바꾸려면 대본에서 수정해주세요"` 안내.
  - 자동 대본 동기화는 **V1**으로 (아래 로드맵).

### 영향 문서
- `PRD V1 로드맵`에 추가: "장소 정체성 교체 시 대본 자동 동기화 (dry_run 고지 + 확인)".
