# Project T — 개발 착수 가이드

> **버전:** v1.0
> **작성일:** 2026-07-31
> **목적:** 설계 문서 6종을 기반으로 Claude Code에게 MVP를 **수직 슬라이스**로 하나씩 만들게 하는 실전 가이드.
> **대상:** antigravity IDE + Claude Code

---

## 0. 핵심 원칙 — 왜 끊어서 시키나

"문서 보고 다 만들어줘"는 금지. Claude Code가 한 번에 너무 많은 걸 만들면 대충 만들고, 검증도 불가능하다.

**수직 슬라이스 = 작동하는 작은 조각을 하나씩 완성해 쌓기.** 골조 → 배관 → 전기 순서로 집을 짓는 것과 같다. 매 단계 실제로 실행해보고 "이건 된다"를 확인한 뒤 다음으로 간다.

**매 단계 지킬 리듬 3가지**
1. **한 단계 끝나면 반드시 직접 실행·테스트.** "다 됐어요"를 믿지 말고 직접 돌려본다. 안 되면 그 단계에서 고치고 넘어간다.
2. **작동하면 git commit.** 다음 단계에서 망가지면 되돌아올 지점.
3. **문서 섹션을 콕 집어 지시.** "네 맘대로 말고 Data-Model 6장 그대로." 즉흥적 이탈 방지.

## 2. 단계별 착수 프롬프트

각 단계는 **만들기 → 직접 실행 → 커밋 → 다음**. 아래 프롬프트를 그대로 복사해 사용.

### 1단계 — 프로젝트 골격 + 인증

```
docs/ 설계대로 개발을 시작하자. 오늘은 1단계만.
Tech-Stack-Decision 문서의 폴더 구조(모듈러 모놀리스)대로
FastAPI 프로젝트 뼈대를 잡고, 인증 부분만 구현해줘.

- API-Spec 1장(인증)의 엔드포인트: OAuth 콜백, GET /me
- Data-Model 2.1의 users 테이블
- 아직 다른 기능은 만들지 마. 인증만 동작하게.

다 만들면 어떻게 실행하고 테스트하는지 알려줘.
```
**확인:** 서버가 뜨고 로그인이 되는가.

### 2단계 — 프로젝트/에피소드 CRUD

```
1단계 좋아. 다음은 프로젝트와 에피소드 관리야.

- API-Spec 2장의 엔드포인트 (프로젝트 생성/조회/삭제, 에피소드 생성)
- Data-Model 2.2, 2.3, 3.1의 projects, project_memory, episodes 테이블
- 소프트 삭제(deleted_at) 포함

인증(1단계)이랑 연결해서, 로그인한 사용자만 자기 프로젝트를 만들 수 있게.
다 되면 테스트 방법 알려줘.
```
**확인:** 로그인 후 프로젝트를 만들고 조회할 수 있는가.

### 3단계 — 게이트 1·2 (텍스트 파이프라인)

```
다음은 게이트 1(기획)과 게이트 2(대본)야.
텍스트 생성이라 이미지 없이 저렴하게 검증할 수 있어.

- API-Spec 3장·4장 엔드포인트
- Backend-State-Model 1장의 gate_status 구조로 게이트 상태 관리
- Gemini API로 텍스트 생성 (Tech-Stack 참고)
- 게이트 2의 대본 수정 시 dry_run 무효화 미리보기(API-Spec 4장)도 포함

아직 이미지·무효화 실행은 빼고, 텍스트 흐름과 게이트 전진만.
```
**확인:** 아이디어 → 시놉시스 → 대본이 나오고, 게이트가 전진하는가.

### 4단계 — 이미지 어댑터 + 게이트 3 (자산 생성)

```
이제 이미지가 처음 들어가는 단계야.

- Tech-Stack 6장의 adapters/ 레이어를 먼저 만들어 (Nano Banana 2 하나만 연결)
- API-Spec 5장의 캐릭터/장소/스타일 엔드포인트
- Data-Model 4·5장의 characters, character_images, character_outfits, locations, styles 테이블
- 이미지 생성은 오래 걸리니 Celery 큐 + job_id 폴링(API-Spec 9장)으로

MVP라 캐릭터 시트는 정면1+표정2, 의상은 default 1벌만 자동 생성. S3 업로드 포함.
```
**확인:** 캐릭터 시트 이미지가 생성돼 S3에 올라가고, job 폴링으로 완료를 확인할 수 있는가.
**주의:** 개발 초기에 Nano Banana 2 API의 연령/실존인물 정책 제약을 Google 문서로 확인.

### 5단계 — 게이트 4·5 (콘티 + 이미지 생성 + 부분 재생성) ★핵심

```
핵심 단계야. 콘티부터 컷 이미지 생성까지.

- API-Spec 6장(콘티), 7장(생성·재생성)
- Cut-Spec-Schema 문서의 컷 명세 JSON 구조 그대로
- Data-Model 6장의 cuts, cut_asset_refs 테이블
- 게이트 4 승인은 과금 경계라 사전 비용 고지 + auto_advance여도 강제 정지
- 부분 재생성, 대사만 수정(과금 없음), 되돌리기 포함
- 컷 이미지 생성 시 캐릭터·장소 레퍼런스 주입

generation_logs에 cost_usd 로깅도 넣어줘.
```
**확인:** 대본 → 컷 명세 → 컷 이미지가 캐릭터 일관성을 유지하며 나오는가. 컷 하나만 재생성이 되는가. **(이 제품의 핵심 가설이 여기서 검증된다.)**

### 6단계 — Export + 과금

```
- API-Spec 8장(Export: PNG/세로1장/인스타 캐러셀)
- Data-Model 7·8장의 generation_logs, 과금 3테이블
- 하이브리드 과금 흐름(구독 할당량 → 초과분 크레딧)
- 결제 PG 연동은 아직 빼고, 크레딧 차감 로직만
```
**확인:** 완성 웹툰을 인스타 캐러셀 규격으로 내보낼 수 있는가. 크레딧이 정확히 차감되는가.

### 7단계 — 무효화 전파 (마지막 통합)

```
마지막이야. 전체 흐름이 도니까 이제 무효화를 통합하자.

- Backend-State-Model 3장의 무효화 전파 규칙
- 규칙 기반 diff 판정(인물/장소 집합 비교)
- 자산 변경 → cut_asset_refs 조회 → 관련 컷 invalidated
- 무효화는 DB 트리거 말고 서비스 계층에서 (문서 5장)
- 무효화돼도 이미지는 유지, stale 표시
```
**확인:** 대본을 고치면 영향받는 컷만 무효화되고, 무관한 자산은 유지되는가.

## 3. 막힐 때 대처

| 상황 | 지시 |
|---|---|
| 문서랑 다르게 만듦 | "그건 API-Spec 5장이랑 달라. 문서대로 다시 해줘." |
| 한 번에 너무 많이 만들려 함 | "이번 단계는 X만. 나머지는 다음에." |
| 뭐가 문제인지 모르겠음 | "지금 이 코드가 뭘 하는지 한국어로 설명해줘." |
| 단계 완료 후 | "이 단계 커밋해줘." |

## 4. 단계 요약 체크리스트

- [ ] 0. 문서 읽히기 (코딩 금지, 요약 확인)
- [ ] 1. 프로젝트 골격 + 인증 → 로그인 확인
- [ ] 2. 프로젝트/에피소드 CRUD → 생성·조회 확인
- [ ] 3. 게이트 1·2 (텍스트) → 시놉시스·대본·게이트 전진 확인
- [ ] 4. 어댑터 + 게이트 3 (자산) → 캐릭터 시트 생성·S3 확인
- [ ] 5. 게이트 4·5 (콘티+이미지+재생성) → **핵심 가설 검증**
- [ ] 6. Export + 과금 → 내보내기·크레딧 차감 확인
- [ ] 7. 무효화 전파 → 부분 무효화 확인

> 각 단계: 만들기 → 직접 실행 → 커밋 → 다음. 서두르지 말 것.
