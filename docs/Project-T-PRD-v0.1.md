# Project T — AI 웹툰 생성 서비스 PRD

> **버전:** v0.1
> **작성일:** 2026-07-31
> **상태:** 초안 (핵심 설계 A~D 확정 반영)
> **한 줄 정의:** 아이디어(대본)를 입력하면, 캐릭터·장소·스타일이 일관되게 유지되는 웹툰 에피소드를 자동 생성하는 서비스.

---

## 0. 문서 목적

이 문서는 Project T의 제품 요구사항을 정의한다. 기능 나열에 그치지 않고, 제품을 실제로 성립시키는 4개의 뼈대를 확정한 결과를 담는다.

- **(A) 파이프라인 + 게이트 구조** — 생성 흐름과 사용자 확정 지점
- **(B) MVP 범위** — 출시 가능한 최소 기능의 커트라인
- **(C) 이미지 스택** — 모델 선정과 일관성(캐릭터/장소/스타일) 구현 방식
- **(D) 과금/원가 구조** — 수익 모델의 뼈대

이 제품의 해자는 스타일 개수나 편집기가 아니라 **여러 컷에 걸친 캐릭터·장소·스타일 일관성 파이프라인**이다. 모든 설계 판단은 이 원칙을 우선한다.

---

## 1. 제품 개요

### 1.1 서비스 철학

Project T는 웹툰을 잘 그리는 사람을 위한 도구가 아니다. **아이디어는 있지만 그림을 그릴 수 없는 사람도 웹툰을 만들 수 있게 하는 것**이 목표다. 창작의 진입장벽을 낮추는 것이 핵심 가치다.

```
기존:  스토리 → 대본 → 캐릭터 → 콘티 → 그림 → 편집 → 업로드   (매우 오래 걸림)
T:     아이디어 → AI → 웹툰 → 업로드
```

### 1.2 핵심 가설

> "대본을 입력하면, 캐릭터 얼굴·장소·화풍이 컷마다 일관되게 유지되는 웹툰 에피소드가 나온다."

MVP의 목적은 이 가설을 최소 비용으로 검증하는 것이다.

## 2. 사용자 (User Personas)

직업보다 **사용 목적**이 기능 설계에 직접적인 영향을 주므로, 목적 중심으로 분류한다.

| 유형 | 주요 목적 | 필요한 핵심 기능 |
|---|---|---|
| **창작형** (Primary) | 새로운 웹툰 제작 | AI 기획·대본·이미지 생성 |
| **콘텐츠형** | SNS 콘텐츠 제작 | 짧은 컷, 세로/정사각 비율, (추후) 영상 변환 |
| **마케팅형** | 제품·서비스 홍보 | 제품 라이브러리, 브랜드 스타일, SNS 업로드 |
| **프로형** | 작업 효율 향상 | 캐릭터 관리, 부분 재생성, 프로젝트 관리 |
| **교육형** | 학습·설명 콘텐츠 | 쉬운 스토리 생성, 교육용 템플릿 |

**핵심 타깃(Primary)은 창작형**이다. "재밌는 이야기가 떠올랐는데 웹툰으로 만들어 SNS에 올리고 싶다"가 대표 시나리오다. 마케팅형·프로형은 확장 사용자로 넓혀간다.

## 3. 파이프라인 + 게이트 구조 (A)

### 3.1 전체 흐름

생성은 자동으로 흐르되, **비싼 단계(이미지 대량 생성) 앞에 사용자 확정 지점(게이트)**을 둔다. 텍스트 생성은 저렴하고 이미지 생성은 비싸므로, 실패를 이르고 싸게 잡는 것이 원칙이다.

```
로그인 · 프로젝트 생성
  │
  ▼
[Story Engine] 아이디어 → 제목·로그라인·시놉시스·세계관·인물목록
  │
  ▼
━━ 게이트 1: 기획 확정 ━━            (텍스트, 무료)
  │
  ▼
[Script Engine] → 화·씬·컷·대사
  │
  ▼
━━ 게이트 2: 대본 확정 ━━            (텍스트, 무료)
  │
  ▼
[Character Engine] 캐릭터 시트 생성 (정면/측면/표정)
[Location Engine]  장소 레퍼런스 생성
[Style Engine]     스타일 프리셋 선택 → 글로벌 스타일 락
  │
  ▼
━━ 게이트 3: 캐릭터·장소·스타일 확정 ━━  (이미지 소액)
  · 여기서 확정된 캐릭터/장소 시트 = 불변 자산
  │
  ▼
[Storyboard Engine] 컷 분할·연출 → 컷 명세(JSON)
  │
  ▼
━━ 게이트 4: 콘티 확정 ━━  ⭐ 승부처   (텍스트/썸네일, 무료)
  · 앵글·컷수·대사·순서 조정 / 컷 추가·삭제·병합
  · 아직 본 이미지 생성 전! 비용 경계선.
  │
  ▼
[Image Engine] 컷별 이미지 생성 (캐릭터·장소 레퍼런스 주입)  ← 💰 대량 과금 시작
  │
  ▼
━━ 게이트 5: 컷 검수 ━━              (부분 재생성 루프)
  · 컷별 OK / 재생성 / 미세조정
  │
  ▼
[Export] PNG · 세로 1장 · 인스타 캐러셀 규격
```

### 3.2 게이트 규칙

**게이트 5개:** 기획 / 대본 / 캐릭터·장소·스타일 / 콘티 / 컷검수

**되돌아가기 — 단방향 + 지능적 무효화**
- 뒤 게이트로 돌아가면 그 이후 산출물은 `invalidated` 상태로 전환되고, 사용자에게 명확히 경고한다.
- 단, diff를 확인해 영향받지 않는 자산은 유지한다. (예: 대본에서 대사만 바뀌고 인물 구성이 그대로면 → 캐릭터 시트 유지, 콘티만 무효화 / 인물 추가·삭제 시 → 해당 인물 캐릭터 시트만 무효화)
- 모든 게이트 산출물은 `status: draft | approved | invalidated` 를 가진다.

**진행 방식 — 기본 정지 + 자동 진행 버튼**
- 기본값은 매 게이트에서 사용자 확인을 위해 정지.
- 각 게이트에 "이후 자동 진행" 버튼 제공. 누르면 다음 게이트들을 사용자 확인 없이 통과.
- **예외: 게이트 4(콘티/비용 경계)는 자동 진행 중에도 반드시 1회 정지한다.** 이미지 대량 생성(과금)이 시작되는 지점이므로 명시적 확인이 필수. (초보의 실수 과금 방어)
- 파이프라인은 하나로 유지되며, "자동 진행"은 사용자 확인만 스킵하는 플래그다.

**비용 경계**

| 게이트 | 산출물 | 비용 |
|---|---|---|
| 1 기획 | 텍스트 | 무료 |
| 2 대본 | 텍스트 | 무료 |
| 3 캐릭터·장소·스타일 | 시트 이미지 | 소액 |
| 4 콘티 | 텍스트/썸네일 | 무료 |
| 5 컷검수 이후 | 본 이미지 | **본 과금** |

## 4. 일관성 아키텍처 — 제품의 해자

### 4.1 자산 모델

게이트 3에서 확정되는 세 가지는 이후 파이프라인 전체에서 **불변 자산**으로 재사용된다.

```
확정 자산 (게이트 3)
├─ 캐릭터 시트   → character_id 로 참조
├─ 장소 레퍼런스 → location_id 로 참조
└─ 스타일 락     → 프리셋 + 시트가 화풍 앵커 겸용

컷 명세: characters[] + location_id + shot + emotion + dialogue ...
컷 생성: 캐릭터 레퍼런스 + 장소 레퍼런스 동시 주입 → 이미지 모델
```

### 4.2 캐릭터 일관성 — 레퍼런스 주입 방식

- 대본 확정 후, 인물별 캐릭터 시트(정면/측면/표정)를 먼저 생성해 사용자에게 확정받는다.
- 확정된 시트는 DB에 불변 자산으로 저장되며, **매 컷 생성 시 레퍼런스로 주입**된다.
- 부분 재생성 시에도 동일한 캐릭터 시트를 물려주므로 얼굴이 흔들리지 않는다.
- LoRA/파인튜닝 방식은 채택하지 않는다(학습 시간·GPU 인프라·비용 부담). 최상급 일관성 수요가 확인되면 V2에서 하이브리드로 검토.

### 4.3 장소 일관성 — 레퍼런스 자산화

- 대본에서 주요 장소(교실/카페/집 등)를 추출해, 장소별 레퍼런스 이미지를 게이트 3에서 함께 확정한다.
- 캐릭터와 동일한 자산 패턴(`location_id` 참조)을 재사용하므로 추가 개발 부담이 작다.
- 해당 장소가 나오는 컷마다 레퍼런스를 주입해 "같은 공간"이 유지되도록 한다.

### 4.4 스타일 락 — 하이브리드

스타일 일관성을 삼중으로 확보한다.

1. **프롬프트 프리셋** — 스타일별 프롬프트 조각을 전 컷 프롬프트에 자동 주입 (Prompt Engine)
2. **캐릭터 시트 앵커** — 해당 스타일로 생성된 캐릭터 시트가 매 컷 주입되며 화풍을 강제
3. **장소 레퍼런스 앵커** — 같은 스타일로 생성된 배경이 화풍을 보강

캐릭터·장소를 자산화한 구조가 스타일 락까지 사실상 공짜로 해결한다. 프롬프트 프리셋은 인물이 없는 배경 컷이나 화풍 보강용으로 작동한다.

## 5. 스타일 시스템

### 5.1 2층 구조

"보이는 선택지 수"와 "품질 보증 부담"을 분리한다. 각 프리셋은 프롬프트 튜닝 + 캐릭터/장소 시트 검증 + 얼굴 일관성 실패율 관리가 필요한 자산이므로, 품질 등급을 나눈다.

**⭐ 코어 프리셋 (완전 검증, 기본값/추천) — 3개**

| 프리셋 | 화풍 | 근거 |
|---|---|---|
| 한국 웹툰체 (네이버풍) | 깔끔한 라인 + 셀채색, 자연스러운 피부톤, 부드러운 그림자 | 세로 스크롤 표준, 최범용·최저 실패율 |
| 순정/로맨스체 | 큰 눈, 얇은 선, 파스텔·핑크톤 | 웹툰 소비 장르 1위권, 상업성 |
| SD/개그체 | 2~3등신, 과장된 표정, 단순 라인 | 마케팅·홍보툰 수요, 진입장벽 낮음 |

**▸ 확장 베타 프리셋 (카테고리 대표 1개씩, `[베타]` 표기) — 약 12개**

| 카테고리 | 대표 프리셋 |
|---|---|
| 웹툰 | 카카오웹툰풍 (화려·강한 명암) |
| 로맨스 | 감성 로맨스 |
| 액션 | 소년만화 |
| 극화 | 반실사 |
| 일본 | 아니메풍 |
| 미국 | 마블풍 |
| 회화 | 수채화 |
| 게임 | 판타지 RPG 일러스트 |
| 특수 | 픽셀아트 |
| 판타지 | 서양 판타지 |
| SF | 네온 사이버펑크 |
| 동화 | 그림책풍 |

- 확장 베타는 프롬프트 프리셋만 준비하고 `[베타]` 뱃지로 기대치를 관리한다. 얼굴 일관성이 코어보다 덜 안정적일 수 있음을 명시.
- **극화/반실사는 얼굴 일관성이 가장 어려운 축이므로 코어가 아닌 베타에 배치**한다.
- 스타일별 **재생성률·완성률을 로깅**해, 잘 되는 스타일을 코어로 승격하고 세부 스타일을 확장하는 데이터 플라이휠을 만든다. (경쟁사가 복제하기 어려운 해자)

### 5.2 UI 노출

```
⭐ 추천 (코어)
   한국 웹툰체 · 순정 로맨스 · SD 개그
─────────────────────────
▸ 웹툰      카카오풍                    [베타]
▸ 로맨스    감성로맨스                  [베타]
▸ 액션      소년만화                    [베타]
▸ 극화      반실사                      [베타]
   ... (카테고리 아코디언, V1에서 세부 점진 확대)
```

### 5.3 로드맵

- **MVP:** 코어 3개 + 확장 베타 ~12개 (프롬프트는 개발 중 튜닝)
- **V1:** 데이터 기반으로 베타→코어 승격, 카테고리 내 세부 스타일 확대(카카오풍→소년만화→다크판타지…), 세부 축(채색/선 굵기/색감/분위기) 조합 제공

## 6. 이미지 스택 (C)

### 6.1 기본 모델 — Nano Banana 2

- **모델:** Nano Banana 2 (`gemini-3.1-flash-image-preview`)
- **선정 근거:** 2026년 기준 레퍼런스 주입 캐릭터 일관성의 사실상 표준. 개발자 API 기준 캐릭터 4명 + 오브젝트 14개까지 일관성 유지. 만화·스토리보드 용도에 강함. 속도·비용 밸런스가 컷 다량 생성에 적합. SynthID 워터마킹 내장(AI 기본법 워터마킹 의무 대응에 유리). Gemini API로 접근해 인증·SDK 공유 용이.
- **연령 정책 확인 필요:** Gemini 앱 기준 이미지 편집이 18세 이상 제약이 있었음 → API 적용 여부를 개발 단계에서 Google 정책으로 확인. 미성년 사용자 수용 시 체크포인트.

### 6.2 어댑터 레이어

- 이미지 모델 호출은 `adapters/` 추상화 레이어를 경유한다.
- **MVP에는 Nano Banana 2 하나만 연결.** 파이프라인은 어댑터만 바라보므로, 향후 모델 교체·추가 시 파이프라인을 건드리지 않는다.
- 표지 컷 등 품질이 결정적인 경우에 한해 향후 Nano Banana Pro(`gemini-3-pro-image-preview`)로 선택 라우팅. (원가는 크레딧에 반영)

## 7. 핵심 기능 목록 & 로드맵 (B)

### 7.1 MVP — 핵심 가설 검증

| 기능 | 범위 |
|---|---|
| 로그인 | 구글 · 카카오 · 네이버 (3종) |
| 프로젝트 생성 | 단순 CRUD |
| AI 스토리 기획 | 아이디어 → 제목·로그라인·시놉시스·세계관·인물 |
| AI 대본 생성 | 화·씬·컷·대사 |
| 캐릭터 시트 ⭐ | 레퍼런스 주입용 시트 생성·확정 (해자) |
| 스타일 선택 | 코어 3개 + 확장 베타 ~12개 |
| 콘티 생성 ⭐ | 컷 분할·연출 → 컷 명세 (게이트 4) |
| 이미지 생성 ⭐ | 컷별 생성 (레퍼런스 주입) |
| 부분 재생성 ⭐ | 컷 하나만 재생성 ("수정=재생성"의 유일 수단) |
| 편집기 | ❌ 없음 |
| Export | PNG(개별 컷) + 세로 이어붙인 1장 + 인스타 캐러셀 규격(1:1 / 4:5) |
| SNS 자동게시 | ❌ 없음 (사용자가 규격 파일 받아 직접 업로드) |

**MVP 설계 원칙**
- **"수정 = 재생성":** 픽셀 편집기를 두지 않는다. 마음에 안 드는 컷은 그 컷만 재생성한다. 캐릭터 일관성 자산과 충돌하지 않고, 원가·개발량을 함께 관리한다.
- **완결 경험 우선:** 인스타는 "규격 이미지 → 직접 캐러셀 업로드"로 경험이 닫힌다. 유튜브는 영상 변환이 선행되어야 하므로 MVP에서 제외(반쪽 기능 배제).

### 7.2 V1 — 정식 출시 (경쟁력)

- 인스타그램 **OAuth 자동 게시** (비즈니스/크리에이터 계정, 앱 심사 선행)
- 웹툰 편집기 (말풍선·효과음·표정·배경 수정)
- AI 감독 채팅 ("더 감동적으로", "표정 슬프게" 등 대화형 수정)
- 스타일 세부 축 조합 + 베타→코어 승격
- 라이브러리 (캐릭터 / 스타일 / 제품)
- 제품 라이브러리 → 브랜드 웹툰 자동 삽입 (마케팅형)
- **참조 이미지 업로드 — 제품/소품 (용도 3):** 사용자가 자사 제품·소품 사진을 올려 장소/소품 자산 생성에 활용. 리스크 낮음(사용자 소유물). 제품 라이브러리와 통합. (상세: 7.6)
- 프로젝트 복제 · 자동 저장

### 7.3 V2 — 고급 기능

- AI 컷 감독(카메라 앵글) / 표정 감독 / 대사 감독
- 버전 관리 (웹툰 V1/V2/V3 비교)
- 협업 (작가·디자이너·마케터)
- 다국어 자동 번역
- 캐릭터 일관성 LoRA 하이브리드 옵션 (프로 티어)
- **참조 이미지 업로드 — 캐릭터 (용도 1):** 본인/권리 보유 사진 기반 캐릭터 시트 생성. **본인 사진 한정 + 업로드 동의 절차 + 유명인 차단 필터** 필수. 초상권·딥페이크 리스크 관리 후 도입. (상세: 7.6)

### 7.4 Future — 장기 로드맵

- 이미지 → 영상 변환 (FFmpeg 파이프라인) → 유튜브/릴스/쇼츠 자동 업로드
- AI 음성 더빙 · 배경음악 · 효과음 자동 생성
- AI 애니메이션 · 립싱크
- API 공개

### 7.5 SNS 업로드 — 방식 정리(참고)

- **비밀번호 입력 대행 방식은 불가.** 메타·구글 정책 위반이며 계정 정지 위험. 유일한 공식 경로는 **OAuth 토큰** 방식(사용자가 직접 권한 승인, 서비스는 토큰 보유).
- **인스타그램 자동 게시:** Content Publishing API(OAuth). 비즈니스/크리에이터 계정 한정, 앱 심사 선행 → V1.
- **유튜브 자동 게시:** ①이미지→영상 변환(FFmpeg) + ②Data API v3(OAuth) 필요. 영상 변환이 큰 덩어리 → Future.

### 7.6 참조 이미지 업로드 — 방식 정리(참고)

사용자가 실사/기존 이미지를 올려 이미지 생성을 보조하는 기능. **레퍼런스 주입 구조에 자연스럽게 얹히나, 법적·정책적 리스크가 기능 난이도보다 크므로 리스크 순으로 단계 도입한다.**

**구조 원칙 — "업로드 → 자산화(확정) → 자산 주입"**
- 업로드 이미지는 매 컷에 직접 주입하지 않는다. **자산(캐릭터/장소)을 만드는 재료**로 들어가 확정되고, 이후는 확정된 자산이 일관성을 담당한다.
- 원본을 매 컷 주입하면 오히려 일관성이 흔들리므로, 반드시 자산화 단계를 거친다.
- 데이터 모델: `characters.source_type`(generated/uploaded) + `source_image_url`, locations 동일. 또는 별도 `user_uploads` 테이블 참조.

**용도별 도입 단계**

| 용도 | 내용 | 리스크 | 도입 |
|---|---|---|---|
| 3. 제품/소품 | 자사 제품·소품 사진 → 배경/소품 자산 | 낮음 (사용자 소유물) | **V1** |
| 1. 캐릭터 | 본인 사진 → 캐릭터 시트 | 높음 (초상권·딥페이크) | **V2** (본인 한정+동의+유명인 차단) |
| 2. 스타일 | 타 웹툰/일러스트 → 화풍 모사 | 매우 높음 (저작권) | **보류** (저작권 정리 전까지 제외) |

**리스크 관리 필수 사항**
- 모든 업로드에 "**본인 또는 권리 보유 이미지만**" 동의 절차.
- 용도 1: 유명인/실존 인물 차단 필터. Nano Banana의 실존 인물 생성 정책 제약 확인 필요(연령 정책과 함께).
- 용도 2: 특정 작가 화풍 모사는 저작권 분쟁 핵심 이슈(국내 AI 저작권 논의 진행 중). MVP·V1에서 제외 권장.

## 8. 시스템 구성 (Backend Services)

프론트엔드 기능과 백엔드 서비스를 분리해 설계한다. 이 서비스는 단순 CRUD가 아니라 **AI Workflow Engine**이다.

```
Frontend → Backend API → AI Workflow Engine → LLM / Image AI / DB / Storage / Queue / Payment / SNS
```

### 8.1 핵심 백엔드 모듈

| # | 모듈 | 역할 |
|---|---|---|
| 1 | Authentication Service | OAuth(구글/카카오/네이버), JWT, 세션, 권한 |
| 2 | User Service | 프로필, 설정, 사용량, 생성 이력 |
| 3 | **Project Service** ⭐ | 프로젝트 생성/저장/복사/삭제/복구/버전 |
| 4 | Story Engine | 아이디어 → 스토리·시놉시스·세계관 |
| 5 | Script Engine | 스토리 → 씬·컷·대사 |
| 6 | **Character Engine** ⭐ | 캐릭터 시트 생성, character_id, 레퍼런스, 메모리 |
| 7 | **Location Engine** | 장소 레퍼런스 생성, location_id |
| 8 | Style Engine | 스타일 프리셋 → 프롬프트 변환 |
| 9 | **Prompt Engine** ⭐ | 컷 명세 → 최종 이미지 프롬프트 조립 (스타일 프리셋 주입) |
| 10 | **AI Context Manager** ⭐ | 프로젝트 전역 일관성 규칙 유지(주인공 외모·의상·말투·금지요소·브랜드 가이드) |
| 11 | Storyboard Engine | 컷 분할·연출 → 컷 명세(JSON) |
| 12 | Image Generation Engine | 컷 명세 + 레퍼런스 주입 → 이미지 → Storage |
| 13 | **Regeneration Engine** ⭐ | 컷 단위 부분 재생성 (같은 명세+레퍼런스, 시드만 변경) |
| 14 | Queue System | 이미지 생성 비동기 큐 (대기/생성/완료) |
| 15 | Token/Credit System | 사용량 계산·차감 (컷 단위) |
| 16 | Export Engine | PNG/세로1장/인스타 규격 |
| 17 | **AI Workflow Engine** ⭐ | 전체 파이프라인 오케스트레이션·게이트 상태 관리 |

**최대 차별점은 AI Workflow Engine과 AI Context Manager**다. 단순 API 호출이 아니라, 여러 AI 작업을 오케스트레이션하고 프로젝트 전체의 일관성을 유지하는 핵심 구성요소다.

### 8.2 컷 명세 스키마 (확정)

컷 명세 JSON은 파이프라인의 척추다. 대본 파싱·콘티·재생성·과금이 모두 이 단위에 물린다. **정밀 스펙은 별도 문서 `Cut-Spec-Schema-v1.0.md`에서 확정**했으며, 핵심 구조는 아래와 같다.

**설계 원칙 — 3분할:** 컷 명세는 콘텐츠만 담고, 생성 결과와 회계를 분리한다.

```
컷 명세 (cut spec)      = 무엇을 그릴지 (콘텐츠). 재생성해도 대체로 유지
  └ generation (객체)   = 지금 표시 중인 이미지 + 재생성 조건 (seed/model/used_references)
generation_logs (테이블) = 매 생성마다 비용 append (회계·cost_usd 실측)
```

재생성 시 한 컷이 여러 번 과금되므로, 비용은 컷 명세가 아니라 append-only 로그로 분리한다.

```jsonc
{
  "cut_id": "ep01_c012",
  "scene_id": "s03",
  "cut_number": 12,
  "characters": [                        // 객체 배열 — 인물별 컷 내 상태
    { "character_id": "hero", "emotion": "surprised",
      "pose": "커피잔을 떨어뜨림", "outfit": "default" },
    { "character_id": "sidekick", "emotion": "laughing",
      "pose": "앉아서 지켜봄", "outfit": "default" }
  ],
  "location_id": "cafe_interior",
  "shot": "close_up",                     // long | full | bust | close_up
  "action": "커피잔을 떨어뜨린다",
  "dialogue": [                          // order + type 으로 말풍선 자동 배치
    { "order": 1, "type": "speech",    "speaker": "hero", "text": "안녕?" },
    { "order": 2, "type": "narration", "speaker": null,   "text": "그날 아침이었다" }
  ],
  "emphasis": "normal",                   // normal | large | full_bleed  (조판 리듬)
  "transition": null,                     // null | scene_break
  "prompt_override": null,
  "status": "pending",                    // pending | approved | regenerating | invalidated
  "generation": {
    "image_url": "s3://.../ep01_c012_v2.png",
    "previous_image_url": "s3://.../ep01_c012_v1.png",  // 되돌리기 1단계
    "seed": 483920,
    "model": "gemini-3.1-flash-image-preview",
    "used_references": ["hero", "sidekick", "cafe_interior", "style:korean_webtoon"],
    "generated_at": "2026-07-31T10:00:00Z",
    "version": 2
  }
}
```

**핵심 결정 사항**
- **캐릭터 = 객체 배열:** 다인 컷에서 인물별 표정·포즈·의상을 개별 지정. `outfit`으로 의상 변화(교복→사복) 표현.
- **대사 = order + type:** `speech`/`narration`/`thought`로 말풍선 모양이 갈리고, 편집기 없이 자동 배치.
- **generation.used_references = 무효화 인덱스:** 별도 의존성 필드 없이, "실제 주입한 자산" 목록을 무효화 기준으로 재사용. 자산 변경 시 해당 자산을 포함한 컷만 `invalidated`. 스타일도 `style:...`로 포함.
- **회계 분리:** `generation_logs` 테이블에 매 생성마다 `cost_usd` append → 재생성 누적 집계 + 가격 확정(9.3)의 근거.
- **대사만 수정은 과금 없음:** 이미지 재생성이 아니라 텍스트 레이어 갱신이므로 크레딧 미차감.

> 전체 필드 정의·재생성 동작표·회계 로그 스키마는 `Cut-Spec-Schema-v1.0.md` 참조.

## 9. 과금 / 원가 구조 (D)

### 9.1 모델 — 하이브리드 (구독 + 초과 크레딧)

- 구독으로 기본 할당량을 제공하고, 초과분은 크레딧 추가 구매.
- 예측 가능한 매출 + 헤비 유저 원가 방어를 동시에 달성.

### 9.2 원칙

- **할당량 단위 = 이미지 컷 수.** 텍스트 단계(기획·대본·콘티)는 원가가 미미하므로 할당량에서 제외하거나 넉넉히 제공하고, 실제 비용이 발생하는 이미지 생성·재생성만 차감한다. → 사용자에게 "이번 달 컷 N개 남음"이 직관적.
- **부분 재생성 = 크레딧 차감.** "수정=재생성" 정책과 정렬. 재생성 전에 "이 작업 N크레딧"을 표시해 투명성 확보(불투명 경쟁사 대비 차별점).
- **모델별 원가 반영.** 향후 Pro 모델 라우팅 컷은 크레딧을 더 차감.

### 9.3 가격 확정 전제

> **정확한 숫자(구독가·할당량·크레딧 단가)는 컷당 `cost_usd` 실측 이후 확정한다.** 개발 중 스타일별·모델별 컷당 실제 API 원가를 로깅하는 것이 선행 과제다.
