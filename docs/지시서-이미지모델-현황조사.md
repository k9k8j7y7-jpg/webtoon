# 지시서 — 이미지 생성 모델 현황 조사 (조사만, 수정 금지)

> **목적:** Project T의 이미지 생성 파이프라인이 현재 어떤 Gemini 모델을 어떻게
> 쓰고 있는지 정확히 파악한다. Nano Banana 2 / Pro로의 업그레이드 판단 자료를 만든다.
> **이 지시서에서는 코드를 한 줄도 수정하지 않는다. 조사와 보고만 한다.**
> **배경 지식:** Nano Banana = Gemini 이미지 생성 라인의 별명.
> - 구형: gemini-2.5-flash-image
> - Nano Banana 2: gemini-3.1-flash-image (범용, 다중 참조·일관성 강점, ~$0.02-0.04/장)
> - Nano Banana Pro: gemini-3-pro-image (최고급, 참조 14장, 5인 캐릭터 일관성, ~$0.134/2K장)

---

## 조사 항목

### A. 현재 모델
1. 이미지 생성에 사용 중인 **정확한 모델 문자열** (백엔드 코드에서 grep.
   후보 검색어: "gemini", "image", "flash-image", "imagen", "generate")
2. 모델 문자열이 하드코딩인가, 설정(환경변수/config)인가? 위치(파일:라인)
3. 텍스트/전략용 모델과 이미지용 모델이 분리돼 있는가? 각각 무엇인가?

### B. 호출 구조
4. 이미지 생성 API 호출 방식: SDK인가 REST인가? 엔드포인트/함수명
5. 배치 구조: 5컷 배치+폴링이 어떻게 구현돼 있는가?
   (동시 요청 수, 폴링 간격, 타임아웃, 재시도 로직)
6. 요청당 파라미터: 해상도, aspect ratio, 기타 생성 옵션 — 실제 코드의 값

### C. 참조 앵커링 (가장 중요)
7. 캐릭터 일관성을 위해 **참조 이미지를 몇 장, 어떻게** 전달하는가?
   - 캐릭터 참조/장소 참조/스타일 참조 각각 몇 장씩인가
   - 요청 페이로드에서 참조 이미지가 들어가는 형식 (inline base64? URI?)
8. 한 컷에 여러 캐릭터가 나올 때 참조는 어떻게 조합되는가?
9. 현재 모델의 참조 이미지 개수 제한에 걸려서 생략되는 참조가 있는가?

### D. 프롬프트 조립
10. 이미지 프롬프트가 조립되는 함수/파일 위치. cut.spec의 어떤 필드가
    프롬프트의 어떤 부분이 되는지 흐름 요약 (5줄 이내)
11. 프롬프트가 모델 종속적인 부분이 있는가? (특정 모델의 문법/키워드 의존)

### E. 비용 산출 근거
12. 최근 에피소드 1개(에피소드 13, 12컷) 기준:
    - 총 이미지 생성 호출 수 (재생성 포함, 로그나 DB에서 확인 가능하면)
    - 확인 불가하면 "계측 없음"으로 보고 (이것 자체가 중요한 확인 사항)
13. 현재 요청 해상도 기준으로, 컷 1장당 대략적 토큰/비용을 코드에서
    역산 가능한가? (가능하면 수치, 불가하면 필요한 정보 명시)

### F. 교체 용이성
14. 모델 문자열을 바꾸면 그대로 동작할 구조인가, 아니면 응답 파싱/요청
    형식이 모델별로 다른 부분이 있는가?
15. 어댑터/추상화 층이 존재하는가? 없다면 이미지 생성 호출부가
    몇 개 파일에 흩어져 있는가? (파일 목록)

## 보고 형식

- 항목 1~15 각각: 답 + 근거 코드 위치(파일:라인)
- 마지막에 요약 3줄:
  ① 현재 모델이 무엇인지
  ② Nano Banana 2 (gemini-3.1-flash-image)로 바꿀 때 코드 변경이
     "문자열 1곳"인지 "구조 수정"인지
  ③ Pro (gemini-3-pro-image)를 쓰려면 추가로 무엇이 필요한지
     (참조 이미지 확장 등)

## 금지 사항

- 코드 수정 금지. 모델 교체 시도 금지. 테스트 호출로 비용 발생시키지 말 것
  (기존 로그/DB 조회는 가능)
- API 키 값을 보고에 포함하지 말 것 (키의 존재 위치만)
