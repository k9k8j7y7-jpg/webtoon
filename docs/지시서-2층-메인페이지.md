# 지시서 — 2층: 로그인·대시보드·패킷·결제·랜딩

> Claude Code에게: 이 문서는 2층(회원·과금·메인 페이지) 전체 구현 지시서다.
> **지금은 0단계(조사·설계)만 수행한다. 1~5단계는 전체 그림 파악용으로만
> 읽고, 각 단계는 이전 단계 완료 + 도도의 "다음 단계 진행해" 승인이 있어야
> 시작한다.** 절대 앞서 나가지 말 것.

## 공통 규칙 (모든 단계)
- 각 단계 완료 시 멈추고 보고. 커밋은 도도 확인 후에만
- 파괴적 git 금지, 미커밋 방치 금지
- **DB 마이그레이션 원칙 (이번엔 실제 마이그레이션이 있다)**:
  project_t_test에서 리허설 → 데이터 포함 백업 → 도도의 "실행해" 승인
  후에만 운영 DB에 적용. 이 순서를 어기는 마이그레이션 금지
- 기존 웹툰 제작 기능(게이트 1~5, 내보내기, 배경효과) 회귀 금지
- 판단이 필요한 지점은 임의로 정하지 말고 멈추고 질문

## 확정된 설계 결정
- 페이지 2개: 비로그인 랜딩 + 로그인 후 대시보드
- 랜딩 구조(elser.ai 구조 참고, 디자인 복사는 금지 — 구성만 참고):
  히어로 → 갤러리(탭 3: 단편/연작/광고·홍보, 큐레이션 방식) →
  3단계 사용법 → 패킷 가격 → FAQ
- 로그인: 소셜만 3사 — 카카오, 구글, 네이버. 이메일/비밀번호 없음
- 패킷: **이미지 생성 1회 = 1패킷 차감** (컷·캐릭터 시트·표정 시트·장소 등
  이미지 호출 전부 동일). **생성 실패(에러) 시 미차감/자동 환불.**
  텍스트(LLM) 작업(콘티·대본 등)은 무료. 신규 가입 무료 패킷 없음.
  판매는 묶음 단위(단가는 추후 원가 계산 후 확정)
- 결제 PG: 토스페이먼츠 (4단계, 가맹 심사는 도도가 별도 진행)
- Q&A: FAQ 정적 페이지 + 1:1 문의 링크 (게시판 없음)
- 알림: 상단 공지 바(운영자 공지) 우선. 개인별 알림은 2차 (종 아이콘
  자리만 확보)
- 갤러리 열람은 비로그인 허용 (공개 뷰어 페이지, 5단계)

## 단계 구성
- 0단계: 현황 조사 + DB 스키마 설계 + 마이그레이션 계획 (조사·설계만)
- 1단계: 소셜 로그인 3사 + users + 기존 데이터 귀속 마이그레이션
- 2단계: 로그인 후 대시보드 (공지 바, 헤더, 내 웹툰 목록, FAQ) + 접근 제어
- 3단계: 패킷 시스템 (잔량, 차감, 실패 환불, 사용 내역, 수동 지급 도구)
- 4단계: 토스페이먼츠 결제 (충전)
- 5단계: 공개 뷰어 + 랜딩 (갤러리 3탭)

## 0단계 — 현황 조사 + 스키마 설계 (지금 할 작업)

**코드 수정 절대 금지. 조사와 설계 문서 작성만 한다.**

### A. 현황 조사 (실제 코드·DB 기준, 추측 금지)
1. 인증 현황: 현재 사용자 식별이 전혀 없는지, 세션/쿠키 등 흔적이 있는지
2. 데이터 구조: projects, series, episodes, cuts 등 주요 테이블(또는 JSON
   구조)과 소유 관계. user_id를 붙여야 할 최상위 소유 단위가 무엇인지
3. 이미지 생성 호출 지점 전수 조사: 컷 생성, 캐릭터 시트, 표정 시트,
   장소 레퍼런스 등 Gemini 이미지 호출이 일어나는 모든 백엔드 위치 목록
   (→ 3단계에서 패킷 차감 훅이 들어갈 자리). 각 지점에서 생성
   실패(에러)를 어떻게 감지할 수 있는지도 함께
4. 프론트 라우팅 구조: 랜딩/로그인/대시보드 페이지를 추가하려면 어디를
   어떻게 건드려야 하는지 (현재 진입 경로 포함)
5. 배포 구조: 세션/토큰을 쓸 때 고려할 것(HTTPS, 도메인, 프록시 등)

### B. DB 스키마 설계안 (제안서 형태로)
1. users: 소셜 3사 대응 (provider, provider_user_id 조합 unique, 닉네임,
   생성일 등). 동일 인물이 카카오·구글로 각각 가입하면 별도 계정으로
   취급한다 (계정 통합은 범위 외)
2. 소유 관계: 최상위 소유 단위 테이블에 user_id FK 추가안
3. 패킷: 잔량 관리 방식(users 컬럼 vs 별도 테이블)과
   packet_transactions(증감 이력: 양수/음수, 사유, 관련 생성 건 참조,
   시각) 설계. 차감·환불이 이력으로 추적 가능해야 함
4. notices: 공지 바용 (내용, 활성 여부, 기간)
5. 각 테이블의 마이그레이션 SQL 초안

### C. 마이그레이션 계획서
1. 기존 데이터 귀속: 현재 있는 모든 프로젝트·시리즈를 "도도 계정"에
   귀속시키는 방법 (도도 계정은 1단계에서 첫 로그인 후 생성됨 —
   귀속 시점과 절차를 어떻게 안전하게 할지 제안)
2. 롤백 계획: 각 마이그레이션의 되돌리기 방법
3. project_t_test 리허설 절차와 백업 절차

### 보고 형식
조사 결과(A) + 스키마 제안(B) + 마이그레이션 계획(C)을 정리해 보고하고
멈춘다. 도도와 Claude(설계 담당)가 검토 후 1단계 지시가 나간다.
설계안은 docs/2층-스키마-설계안.md 로 저장해도 좋다 (커밋은 승인 후).

## 1~5단계 개요 (승인 전 시작 금지)

**1단계 — 소셜 로그인**: 카카오·구글·네이버 OAuth (앱 키는 도도가 발급해
전달), 콜백 처리, 세션/토큰, users 생성, 로그인 화면. 기존 데이터 귀속
마이그레이션 실행(원칙 준수). 로그인 없이는 제작 기능 접근 불가 처리는
2단계 접근 제어와 함께.

**2단계 — 대시보드**: 공지 바(활성 공지 1건 노출, 닫기 기억), 헤더(로고·
패킷 배지 자리·종 자리·프로필), 내 웹툰 목록(+새로 만들기), FAQ 페이지,
접근 제어(본인 소유만 조회·수정 가능 — 백엔드 검증 필수).

**3단계 — 패킷**: 이미지 생성 경로 전부에 차감 훅(0단계 조사 목록 기준),
잔량 부족 시 생성 차단 + 안내, 실패 시 자동 환불(트랜잭션 이력 필수),
대시보드 패킷 현황(잔량·사용 내역), 도도용 수동 지급 방법(관리 스크립트
수준이면 충분).

**4단계 — 토스페이먼츠**: 충전 상품(묶음) 정의, 결제 위젯 연동, 결제 승인
콜백 → 패킷 지급(멱등 처리 필수 — 중복 지급 방지), 결제 내역. 테스트
키로 개발 → 도도 가맹 심사 완료 후 라이브 키 전환.

**5단계 — 공개 뷰어 + 랜딩**: 에피소드 공개 뷰어(비로그인, 세로 스크롤,
공유 URL), 작품 갤러리 노출 플래그, 랜딩 페이지(히어로·갤러리 탭 3·
사용법·가격·FAQ). 디자인 시안은 Claude(설계 담당)가 별도 제공 예정.
