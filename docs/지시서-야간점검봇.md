# 지시서 — 출시 준비 B: 백업·정상 기동·야간 점검 봇

> 목적: 도도가 안 보고 있어도 **(1) 매일 백업이 남고 (2) 서버가 제대로 떠 있고 (3) 밤마다 점검해서 아침에 푸시로 요약, 심각하면 메일**까지 오게 한다. 통계 페이지의 `app/admin/checks.py`를 그대로 재사용한다.
> 순서: **1단계 조사 → 보고 → 도도 "실행해" → 2단계(A 백업 → B systemd → C 봇 → D 알림) → 검증 → 커밋**. 서버 설정(sudo·crontab·systemd·.env)은 **백업 → diff 보여주기 → "실행해" → 적용 → 확인** 규칙. 비밀번호·키는 채팅·명령줄 금지(도도가 서버 .env에 직접 입력).

## 1. 1단계 — 조사 (보고 후 대기)
① `crontab -l`(bitnami·root), 기존 systemd 유닛(`systemctl list-units | grep -i uvicorn`), 현재 uvicorn 기동 방식(11/17부터 `--reload`로 수동 실행 중 — 누가 어떻게 띄웠는지, 재부팅 시 자동 기동 여부), Apache 재시작 방식.
② 백업 현황: ~/backups/ 목록·크기, storage/ 총 용량, DB 덤프 1회 소요 시간·크기(테스트 DB로 측정).
③ 푸시: 기존 웹푸시 코드(VAPID, 구독 테이블, 관리자 계정 구독 여부, 발송 함수 위치). 메일: 발송 코드 유무(없을 것으로 예상).
④ SSL 인증서 만료일(`certbot certificates` 또는 openssl), `/health` 엔드포인트 유무(외부 `https://ssagda.com/WEBTOON/health`, 내부 `http://127.0.0.1:8000/health` — `/api/health`·`ssagda.com/api/health`는 없음).
⑤ 설계 제안서: systemd 유닛 파일 초안, 배포 스크립트 변경(scp 후 `systemctl restart`), cron 표(시각 KST), 봇 모듈 구조. **적용은 하지 않음.**

## 2. 2단계 — 구현

### A. 백업 (cron, bitnami 계정)
- 매일 **04:10 KST** `~/bin/backup_db.sh`: mysqldump project_t(비밀번호는 `~/.my.cnf` 600 권한 — 도도가 입력, Claude Code는 파일 존재만 확인) → `~/backups/daily/project_t_YYYYMMDD.sql.gz`, **14일 보관**, 실패 시 종료코드≠0 + 로그 `~/backups/backup.log`.
- 매주 **일요일 04:40** `~/bin/backup_storage.sh`: `/home/bitnami/project-t/storage/` → `~/backups/storage/storage_YYYYMMDD.tar.gz`, **2개 보관**. 실행 전 디스크 여유 < 20%면 건너뛰고 로그.
- 봇 체크 `backup`은 daily 24h 이내·storage 8일 이내를 본다.
- **도도 할 일(서버 밖 복제)**: Lightsail 콘솔 → 인스턴스 → 스냅샷 → 자동 스냅샷 켜기(일 1회, 7일 보관). Claude Code가 클릭 순서 안내만.

### B. 정상 기동 (systemd)
- `/etc/systemd/system/ezitoon-api.service`: `uvicorn app.main:app --host 127.0.0.1 --port <현재 포트> --workers 2`(**--reload 제거**), `Restart=always`, `RestartSec=3`, `User=bitnami`, `WorkingDirectory=/home/bitnami/project-t/backend`, `EnvironmentFile=` 서버 .env, 로그 journald. `enable` + 재부팅 자동 기동.
- 배포 스크립트(scp 후): `sudo systemctl restart ezitoon-api && sleep 3 && curl -fsS http://127.0.0.1:8000/health | grep -q '"status":"ok"' && curl -fsS https://ssagda.com/WEBTOON/health | grep -q '"status":"ok"'`. 실패 시 중단·보고. **`-f`만으로는 부족** — 없는 경로도 SPA fallback이 200 HTML을 돌려주므로 JSON `"status":"ok"` grep 필수.
- `GET /health`(백엔드 라우트, Apache `ProxyPass /WEBTOON/ → localhost:8000/`이라 외부는 `https://ssagda.com/WEBTOON/health`): `{status, db:ok, time, version(git hash)}` 인증 없음, 캐시 없음.
- 전환 절차: 현재 프로세스 기록 → 유닛 파일 diff 보고 → "실행해" → 기존 수동 프로세스 종료 → `systemctl start` → health 200·JSON `"status":"ok"` → 사이트 로그인·내 작품 로드 확인. **생성 작업 진행 중이면 대기.**
- journald 용량 제한(`SystemMaxUse=500M`) + logrotate 확인.

### C. 야간 점검 봇
- `backend/app/admin/nightly_check.py` (`python -m app.admin.nightly_check`), cron **03:30 KST**(백업 전). 흐름: `run_all_checks(source="bot")` + **model_smoke 포함**(밤 1회, 약 200원) + 추가 체크:
  - `http`: `https://ssagda.com/WEBTOON/` 200, `https://ssagda.com/WEBTOON/health` 200·JSON `"status":"ok"`·db ok, 응답 2초 이내(warn 5초)
  - `ssl`: 인증서 만료 D-14 warn / D-7 fail
  - `backup`(위 A 기준), `disk`, `failed_jobs`, `packet_ledger`, `api_errors`(402·404·429), `inquiries`, `exchange_rate`, `prices_missing`, `apache_config`, `systemd`(ezitoon-api active·최근 24h 재시작 횟수 warn ≥3)
  - `script_smoke`: 테스트 계정(u1) 한 컷 광고 에피소드 생성 → `POST /script` 대본 1회 → 성공 확인 → 에피소드 삭제(무료, 0패킷). 11-20 대본 500 17시간 사건(792c2ae 로컬 import 충돌) 재발 방지
  - `cost_today`: 어제 API 원가 합이 최근 7일 평균의 3배 이상이면 warn(폭주 감지), 패킷당 원가가 299원 넘으면 warn
- 결과 admin_checks(source=bot) 저장 → 요약 생성 → D 알림. 체크 하나가 예외여도 나머지 진행, 예외는 fail로 기록.
- 상태 탭에 "마지막 야간 점검 HH:MM · 정상 N / 주의 N / 심각 N" + 봇 이력 7일.

### D. 알림
- **푸시(매일)**: 관리자 계정의 웹푸시 구독 전부에 `"야간 점검 11-20 · 정상 12 / 주의 1 / 심각 0 — 미답변 문의 1건"`. 전부 정상이어도 보낸다(안 오면 봇이 죽은 것). 클릭 → /admin 상태 탭.
- **메일(심각일 때만)**: fail ≥1이면 `ADMIN_EMAIL`로 제목 `[이지툰 점검] 심각 N건 — 11-20`, 본문 체크별 상태·값·설명. SMTP 값은 서버 .env: `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, `SMTP_FROM`, `ADMIN_EMAIL`(도도 입력). 네이버 메일 기준 `smtp.naver.com:587 STARTTLS`(도도: 네이버 메일 환경설정 → POP3/IMAP → SMTP 사용 켜기, 2단계 인증이면 앱 비밀번호).
- 발송 실패도 admin_checks에 `notify_push` / `notify_email` 행으로 남김. 상태 탭에 "마지막 푸시 수신 시각"은 도도가 확인.
- 봇 자체가 안 돌면? → 상태 탭에 "야간 점검 24h 이상 없음" 빨간 카드(페이지 열 때 계산).

### E. 문서
- docs/운영-점검.md: cron 표, systemd 명령 5개(status·restart·logs), 백업 복원 절차(daily 덤프 → project_t_test 복원 → 확인), 알림 해석법, .env 키 목록(값 없이). CLAUDE.md 운용 주의에 "배포 = scp → systemctl restart → health" 한 줄, `--reload` 금지.

## 3. 검증
① A: `backup_db.sh` 수동 1회 → 파일 생성·크기 → **project_t_test에 복원 리허설** 성공(행 수 비교 표). storage 스크립트 수동 1회(용량·시간).
② B: systemd 전환 후 health 200·사이트 로그인·테스트 계정 onecut 1패킷 생성 OK·`systemctl status` active·`sudo reboot`는 하지 않음(대신 `kill` 후 3초 내 자동 재기동 확인).
③ C: `python -m app.admin.nightly_check` 수동 1회 → admin_checks 행 목록·요약 문자열 보고 → **도도 폰에 푸시 수신(도도 확인)**. fail 스텁(디스크 임계값 임시 1%)로 1회 더 → **메일 수신(도도 확인)** → 스텁 원복.
④ cron 등록 내용 `crontab -l` 캡처, 다음날 아침 도도 푸시 수신으로 최종 확인(HANDOFF에 기록).
⑤ 상태 탭 캡처(마지막 야간 점검·봇 이력) 1280·375.

## 4. 금지·주의
- sudo·crontab·systemd·.env 변경은 백업·diff·"실행해" 후. 비밀번호·앱 비밀번호·VAPID는 채팅·명령줄·로그 금지(VAPID 3곳 재생성 금지). 도도가 입력할 값은 **nano 열어주는 명령까지만** 안내.
- 생성 로직·프롬프트·패킷·가격 불변. 운영 DB SELECT만(복원 리허설은 project_t_test).
- 커밋 2개: `ops: 백업 cron + systemd 정상 기동 + /api/health` → `feat: 야간 점검 봇 + 푸시·메일 알림`. 각각 도도 확인 후.
